Go packages for integrating [yardrail](https://github.com/yardrail/yardrail) with external services. Each service produces a typed Go client, an MCP server package, or yardrail connector code generated from a manifest. Yardrail imports these packages directly.

This repo also holds the API specs and codegen tools used to produce those packages.

## Prerequisites

This repo uses [mise](https://mise.jdx.dev/) to manage tool dependencies. Run `mise install` to set up the required tools:

| Tool             | Purpose                              |
| ---------------- | ------------------------------------ |
| `node`           | npm tools for spec conversion        |
| `oapi-codegen`   | Generate Go clients from OpenAPI     |
| `task`           | Task runner for the build pipeline   |
| `trivy`          | Security scanning                    |

All tools are pinned in `.mise.toml`. The Go toolchain version is declared in each module's `go.mod`.

## Repository structure

```
connectors/
├── Taskfile.yml                    # Root orchestration — includes all vendors
├── tools/                          # Shared codegen utilities (separate Go module)
│   ├── cmd/
│   │   ├── gen-readme/             # Generates this README from a template
│   │   ├── mcp-openapi-codegen/    # Generate MCP server from an oapi-codegen client
│   │   └── yardrail-connector-codegen/  # Generate yardrail connector code from a manifest
│   └── codegentest/                # Connectors generated from codegen fixtures, with runtime tests
└── <company>/
    ├── Taskfile.yaml               # Vendor-level — aggregates products
    ├── tools/                      # Vendor-specific codegen (optional, e.g. quickbooks/tools/)
    └── <product>/
        ├── Taskfile.yaml           # Product-level — standard entrypoints
        ├── go.mod
        ├── spec/                   # API contract (OpenAPI, GraphQL SDL, etc.)
        ├── client/                 # Generated typed Go client (OpenAPI only)
        └── mcp/                    # Generated MCP server package
```

Services are nested `company/product`. Single-product companies repeat the name (`slack/slack/`,
`canva/canva/`). Each product is its own Go module with standalone dependencies.

## Service archetypes

- sdk-backed
- spec-generated
- graphql

### SDK-backed

Services with an official Go SDK (e.g. Google Sheets via `google.golang.org/api/sheets/v4`). No `spec/` or `client/` — `go.mod` depends on the SDK directly and `mcp/` is generated from it.

```
google/sheets/v4/
├── go.mod
├── doc.go
└── mcp/
    ├── generate.go     # //go:generate mcp-google-codegen ...
    └── tools_gen.go
```

### Spec-generated

Services without a usable Go SDK — client and MCP packages are generated from the API spec.

```
officernd/officernd/
├── go.mod
├── spec/
│   └── openapi.json
├── client/
│   ├── generate.go     # //go:generate oapi-codegen -config cfg.yaml ../spec/openapi.json
│   ├── cfg.yaml
│   └── client_gen.go
└── mcp/
    ├── generate.go     # //go:generate mcp-openapi-codegen ...
    └── tools_gen.go
```

### GraphQL

GraphQL APIs with hand-written operations. No typed Go client yet (planned). See each connector's README for manifest and operation conventions.

```
monday/monday/
├── go.mod
├── manifest.yaml
├── spec/
│   └── schema.graphql
└── operations/
    ├── GetItem.graphql
    └── ...
```

## Generation pipeline

Connector generation follows a three-stage pipeline:

```
  ┌─[ spec ]───────────────────────────────┐   ┌─[ client ]─────────────────┐   ┌─[ connector ]────────┐
  │ acquire/generate the API defintion     │   │ generate typed Go client   │   │ generate yardrail    │
  │                                        │   │ from spec                  │   │ connector + CWL code │
  │                                        │   │                            │   │                      │
  │                                        │   │                            │   │                      │
  │ schema collection ──► openapi.json    ───────►  oapi-codegen ────┐      |   │                      │
  |                                        │   │                     ▼      │   │                      │
  | schema collection ──► schema.graphql  ───────►  (planned) ───► client  ───────► connector-codegen  │
  |                                        │   │                     ▲      │   │                      │
  │ sdk                                   ───────►  (planned) ───────┘      │   │                      │
  │                                        │   │                            │   │                      │
  └────────────────────────────────────────┘   └────────────────────────────┘   └──────────────────────┘

```

Run any stage for a single connector (`task slack:spec`) or everything (`task spec:all`). Each stage depends on the previous — running `task slack:connector` automatically runs `spec` then `client` first.

The variation is in the `spec` and `client` stages — the goal is for every archetype to produce a typed Go client so that `connector` always consumes the same artifact.

For OpenAPI connectors, the spec stage varies by vendor:

| Connector       | Spec source                          | `spec` task                                                              |
| --------------- | ------------------------------------ | ------------------------------------------------------------------------ |
| Most connectors | Committed `openapi.json` from vendor | No-op (manually updated)                                                 |
| QuickBooks      | XSD + JSON proprietary schemas       | Runs `specgen` tool to produce OpenAPI                                   |
| Eventbrite      | API Blueprint (`.apib`)              | Multi-step conversion: apib → swagger2 → fixup.py → openapi3 → fixup.py |

Many upstream specs need fixups before codegen can process them. When a spec needs programmatic fixes, place a `fixup.py` in `spec/` and call it from the `spec` Taskfile target. See `eventbrite/eventbrite/spec/fixup.py` for an example.

## Codegen tools

Shared codegen commands live in `tools/`, which is its own Go module (`github.com/yardrail/connectors/tools`). Product-specific codegen lives under the company directory (e.g. `google/tools/`, `quickbooks/tools/`).

| Command                      | Location            | Purpose                                                                                                        |
| ---------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------- |
| `mcp-openapi-codegen`        | `tools/`            | Generate MCP server package from an oapi-codegen client                                                        |
| `yardrail-connector-codegen` | `tools/`            | Generate yardrail connector handler, dispatch, catalog entry, CWL schema and CWL class mapping from a manifest |
| `mcp-google-codegen`         | `google/tools/`     | Generate MCP server package from a Google Go SDK                                                               |
| `specgen`                    | `quickbooks/tools/` | Generate OpenAPI spec from Intuit XSD schemas                                                                  |

Service packages invoke the MCP generators via `//go:generate` directives in `generate.go` files. `yardrail-connector-codegen` runs from each connector's `connector` Taskfile target.

## Taskfile reference

### Per-connector tasks

Every connector exposes standard entrypoints through hierarchical Taskfiles. Replace `<vendor>` with the vendor name (e.g. `slack`, `quickbooks`):

| Task                      | Description                                            |
| ------------------------- | ------------------------------------------------------ |
| `task <vendor>:spec`      | Acquire or generate the API spec                       |
| `task <vendor>:client`    | Generate the typed Go client (depends on `spec`)       |
| `task <vendor>:connector` | Generate yardrail connector code (depends on `client`) |
| `task <vendor>:build`     | `go build ./...`                                       |
| `task <vendor>:test`      | `go test ./...`                                        |
| `task <vendor>:vet`       | `go vet ./...`                                         |
| `task <vendor>:lint`      | vet + build + test in sequence                         |

### Aggregate tasks

| Task                 | Description                                      |
| -------------------- | ------------------------------------------------ |
| `task spec:all`      | Run spec acquisition for all connectors          |
| `task client:all`    | Generate clients for all connectors              |
| `task connector:all` | Generate connector code for all connectors       |
| `task build:all`     | Build all connector modules                      |
| `task test:all`      | Run tests across all connector modules           |
| `task vet:all`       | Run `go vet` across all connector modules        |
| `task lint:all`      | Run vet + build + test for all connector modules |

### Tool and utility tasks

| Task                  | Description                                                                      |
| --------------------- | -------------------------------------------------------------------------------- |
| `task build:tools`    | Build all codegen tool binaries (`tools/`, `quickbooks/tools/`, `google/tools/`) |
| `task test:tools`     | Run tests for all codegen tools                                                  |
| `task docs:readme`    | Regenerate README.md from template                                               |
| `task list:modules`   | List all Go modules in the repo                                                  |

## Adding a new service

1. Create the directory: `mkdir -p <company>/<product>/{spec,client,mcp}`
2. Initialize the module: `cd <company>/<product> && go mod init github.com/yardrail/connectors/<company>/<product>`
3. Copy in the API spec to `spec/` — apply any necessary fixups
4. Create `doc.go`, `client/generate.go`, `client/cfg.yaml`, `mcp/generate.go` (copy from an existing connector of the same archetype)
5. Create Taskfiles at the vendor, product, and version levels (copy from an existing connector of the same archetype)
6. Wire the vendor Taskfile into the root `Taskfile.yml` includes block and add the vendor to each `*:all` aggregate task
7. Run `task <vendor>:client` to generate the client (runs `go mod tidy` automatically)
9. Run `go generate ./mcp/` then `go mod tidy` (MCP generation is not yet wired into the Taskfile pipeline)
10. Verify with `task <vendor>:build`
